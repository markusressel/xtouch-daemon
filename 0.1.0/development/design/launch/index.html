Design: launching applications from a strip¶

Status: implemented as described here; how to use it is in Applications and VoIP.

The idea: the Select button of a strip whose application is not there starts it. A "VoIP" strip starts Mumble and connects it to the server, a "Music" strip starts the music player.

Where Select is free¶

Strip type What Select does without launch launch
output, input makes the device the default (select), or nothing not allowed: Select is taken
apps nothing allowed
auto nothing allowed
voip shows the next page of participants (the LED is on while there are several pages) allowed: Select launches while the voice chat is not there, and pages as before while it is
homeassistant an event in Home Assistant not allowed: Home Assistant owns the strip and can never send a command
empty, inherit nothing / the inherited strip's not allowed / the inherited strip's

Validation is by pydantic: an unknown option on the other types is an error already (extra = "forbid").

Configuration¶

[[strip]]
type = "apps"
match = ["discord", "webrtc", "teamspeak", "ts3client", "signal", "mumble"]
label = "VoIP"
launch = ["mumble", "mumble://markus@voice.example.org/Gaming"]
  • launch: the program, then its arguments, as a list. It must not be empty, and no part may be empty.
  • A single string is accepted too and split with shlex.split (quotes like a shell, nothing expanded: no ~, $VAR, globs, pipes or &&). Decided for it because a command line is what people copy from a .desktop file or a terminal, and the GUI's list of chips stays the canonical form (it saves a list). The split happens at validation, so check-config and the GUI show the parts.
  • launch_when_running (apps, auto): Select starts the command also while the application runs. For Mumble that is useful: a running Mumble takes the URL and connects (see below), and mumble without a URL brings its window to the front. Not on voip strips, where Select pages while the voice chat is there.

Mumble URLs¶

From the Mumble documentation:

mumble://[username[:password]@]<address>[:port]/[channelpath][?title=<servername>][&url=<serverurl>]
  • The port defaults to 64738. Special characters of the channel path must be URL-encoded (Gaming%20Night). Subchannels are separated by /. When the channel can't be reached, Mumble stays in the default channel.
  • ?version=1.2.0 was needed only before Mumble 1.2.4. title and url matter only when the link is dropped into the server browser.
  • A password in the URL ends up in the configuration file and in the process list (/proc/*/cmdline is readable by every user). Leave it out and let Mumble remember it, or use a certificate.

A running Mumble accepts the URL too: on Linux, Mumble's main.cpp hands the URL of a second instance over D-Bus (openUrl on info.mumble.mumble, then the legacy net.sourceforge.mumble.mumble) to the running one and exits; without a URL it asks the running one to focus. Only --multiple starts a second client. Verified in the source (src/mumble/main.cpp), not with a real Mumble.

When an application "runs"¶

Select launches only while none of the strip's applications runs. "Runs" for each type:

Strip type Runs while
apps a stream matches match, or a process whose name contains one of the match entries runs, or the program of launch runs
auto the strip has an application (it plays, was picked, or its hold time is not over), or the program of launch runs
voip the provider reports the voice chat (connected: the Mumble plugin is there, also while nobody talks), or the program of launch runs
  • Processes are matched like the processes rule of layouts (layouts.process_matching()): the names from layouts.running_processes() (the kernel's comm and the file name of the program, in lower case), containing the pattern. So a silent Mumble (no stream) counts as running.
  • The program of launch is the file name of its first part, matched exactly, not as a part: flatpak must not match flatpak-portal, which runs all the time. For ["flatpak", "run", "info.mumble.Mumble"] that is useless (the program is flatpak), so name the application in match (mumble matches the process inside the sandbox).
  • The processes are read every 2 s (mixer.PROCESS_INTERVAL, like the layout rules), only while a strip of the layout has launch.
  • A match entry like signal also counts unrelated processes whose name contains it. The cost is a Select that does nothing; list-apps and ps -e show what runs.

Starting it¶

  • Never through a shell. The list goes to exec as it is.
  • Detached from the daemon's service. With a systemd user manager (its socket $XDG_RUNTIME_DIR/systemd/private) and systemd-run in PATH: systemd-run --user --quiet --collect --unit=xtouch-launch-<program>-<random> --property=WorkingDirectory=~ -- argv…. Otherwise a plain process in a session of its own (start_new_session), stdin/stdout/stderr on /dev/null, waited for by a thread so it does not stay a zombie.
  • Deviation from the first idea, systemd-run --scope: a scope runs the command as a child of systemd-run, which is a child of the daemon, with the daemon's environment. The daemon's service starts with default.target, often before the desktop imports WAYLAND_DISPLAY/DISPLAY into the user manager, so a GUI application started from a scope may find no display. A transient service gets the user manager's environment of the moment, is not a child of the daemon (no zombie, survives a restart of the daemon without question), and its output goes to the journal (journalctl --user -u 'xtouch-launch-*'). --collect removes the unit also when it failed.
  • Logging: every start is logged (info, with the command), a program that is not in PATH is a warning (checked before, with shutil.which, so systemd-run does not fail later in the background), an OSError of the start a warning, an exit of the started process with an error code (fallback mode, or systemd-run itself) a warning. A launch that does not show up in 15 s is a warning. Nothing of it stops the daemon.
  • Debounce: no second launch within 5 s (LAUNCH_DEBOUNCE) of the last one while the application is not up yet, so a double press starts it once.
  • Reload: the launch state belongs to the strip and starts anew with a reload or a layout switch; the started application is not affected.

The Select LED¶

Strip type LED with launch
apps, auto flashes while launching (until the application runs, at most 15 s, LAUNCH_TIMEOUT), on while it runs, off otherwise. Without launch it stays off, as before.
voip flashes while launching, then as before: on while there are several pages. "On while it runs" would hide the paging, which is the older meaning.

The device flashes the LED itself (Mackie Control Led.FLASH), the daemon sends it once.

Security¶

  • Commands come only from the configuration: the file, or the configuration of a live preview. The live view only accepts clients of the same user (SO_PEERCRED in live.py), who could edit the file anyway. A preview whose launch runs something is no more than that user can do in a shell.
  • Home Assistant and MQTT can never send a command: nothing arriving over MQTT reaches launch, and homeassistant strips can't have it.
  • No Home Assistant button entity for now. A button per strip that runs the configured command would be safe (it runs only the configured command, never one from MQTT), but it lets anyone who can press buttons in Home Assistant start programs on the desktop, also while nobody sits there. Left out until there is a use for it.

Later¶

  • Focus the window when Select is pressed while the application runs. On Wayland there is no portable way (KWin scripts, GNOME extensions, the Sway/Hyprland IPC differ, see Layouts). For Mumble, launch_when_running with launch = ["mumble"] already does it through Mumble's own D-Bus focus.
  • A launch_process option for commands whose program is not the application (flatpak run, gtk-launch), if match turns out not to be enough.
  • A Home Assistant button (see Security).

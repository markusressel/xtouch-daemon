Commands¶

Command What it does
xtouch-daemon run Runs the daemon in the foreground.
xtouch-daemon check-config Validates the configuration, describes its channels and shows what the slots show when.
xtouch-daemon init-config Writes the example configuration.
xtouch-daemon schema Prints the JSON Schema of the configuration, for editors.
xtouch-daemon list-devices Lists outputs, inputs, and the sound cards with their profiles.
xtouch-daemon list-apps Lists the applications that play, and which channel or slot takes each one.
xtouch-daemon test Tests the LCDs, LEDs, rings, meters and faders, then shows what happens on the device.
xtouch-daemon virtual-device Runs a virtual X-Touch Extender, for trying the daemon without the device.
xtouch-daemon mode Shows the running daemon's mode, or picks another one.
xtouch-daemon why Says why a slot shows what it shows, or where a channel is and why.
xtouch-daemon mumble-plugin Shows, builds or installs the Mumble plugin for the strips of people.
xtouch-daemon install-service Sets the daemon up as a systemd user service.
xtouch-daemon gui Edits the configuration in a window.
xtouch-daemon simulate What the slots of a configuration show in a situation you give it.
xtouch-daemon observe Records what plays, records and runs, for simulate --replay.

Every command takes -h/--help. xtouch-daemon -V (--version) shows the version.

-c FILE (--config FILE) selects the configuration file; the default is ~/.config/xtouch-daemon/config.toml.

run¶

xtouch-daemon run [-c FILE] [-l LEVEL] [--virtual-device]

Runs the daemon in the foreground. install-service sets it up as a systemd user service instead.

Option Meaning
-c, --config FILE The configuration file.
-l, --log-level LEVEL debug, info (default), warning or error. debug also logs the messages of the device the daemon doesn't use.
--virtual-device Drives the virtual device instead of the real one, as [device] virtual = true.

The daemon notes its process and configuration file in $XDG_RUNTIME_DIR/xtouch-daemon.json while it runs, and serves what the device shows on $XDG_RUNTIME_DIR/xtouch-daemon.sock for the GUI. A second daemon does not start: it names the one that runs.

Signals:

Signal Effect
SIGHUP Reloads the configuration (systemctl --user reload xtouch-daemon), as the daemon does by itself when the file changes. A file with errors is logged, and the current configuration stays.
SIGTERM, SIGINT Stops: the strips go dark from the right and the faders go down.

check-config¶

xtouch-daemon check-config [-c FILE] [--all]

Validates the configuration, describes each channel and shows a table of what the slots show in which states. Without a file at the default path it checks the defaults. Example output:

/home/me/.config/xtouch-daemon/config.toml: valid
Channels:
  out: 'Speaker' output alsa_output.pci-0000_11_00.4.analog-stereo, select makes it the default (cyan, rec: recording, solo: off, encoder: balance)
  mic: the default input (red, rec: recording, solo: off, encoder: balance)
  browser: 'Browser' applications @browsers (firefox, chromium, ...) (yellow, rec: recording, solo: off, encoder: media)
  lamp: 'Living' Home Assistant, entities *.*_lamp_* (yellow)
What the slots show:
when     1    2        3     4-8
default  out  browser  auto  auto
call     out  browser  mic   auto

A channel with choices lists them, e.g. output: Phones, Speaker or Buds (Select switches). A channel whose meter shows the level after its fader (meter_point = "post_fader", see Meters) says meter post-fader.

A custom channel describes each bound part with its programs; with targets, a line per target follows with the programs as they run for it, e.g. Left: fader.set sysctrl display redshift brightness -d DisplayPort-1 -b '{value}'.

A table of more than 12 rows shows the situations that differ in one thing; --all shows every combination.

A file with errors names the place of each one and its line in the file, e.g. channel.mic (line 12): label: String should have at most 7 characters, with what is likely meant where it can be guessed (browsr is no channel or pool (did you mean browser?)), and the command fails. After the table, Notes: lists candidates that can never show (e.g. a channel below a pool without a condition) and people with no slot to sit on.

init-config¶

xtouch-daemon init-config [PATH] [-f]

Writes the example configuration with channels, states and slots to ~/.config/xtouch-daemon/config.toml, or to PATH. An existing file stays, unless -f (--force) overwrites it.

schema¶

xtouch-daemon schema > ~/.config/xtouch-daemon/config.schema.json

Prints the JSON Schema of the configuration of the installed version. Editors with a TOML language server complete the options from it and show their help.

list-devices¶

xtouch-daemon list-devices [--snippet]

Lists the outputs and inputs with the node names to use as device, their descriptions, volumes and states; * marks the defaults. Then it lists each sound card by its name and description, with its devices and its profiles (name and description), for card and profile of choices and for profiles; * marks the active ones. --snippet prints a [channel.<id>] for each device instead, ready to paste into the file (Bluetooth devices by a wildcard like bluez_output.*, since their names hold the address of the device):

Profiles of alsa_card.pci-0000_11_00.4, Family 17h/19h HD Audio Controller (alsa_output.pci-0000_11_00.4.analog-stereo):
  * output:analog-stereo+input:analog-stereo
      Analog Stereo Output + Analog Stereo Input
    output:iec958-stereo+input:analog-stereo
      Digital Stereo (IEC958) Output + Analog Stereo Input

list-apps¶

xtouch-daemon list-apps [-c FILE]

Lists the applications that play now: their names (and aliases), the presets they are part of (e.g. Brave (@browsers)), binaries and volumes, and where each one goes: the apps channel that has it, an auto or apps slot, "ignored" (exclude of [pool.apps]) or no slot. Use the names and binaries, or the presets, for match, exclude and [aliases].

test¶

xtouch-daemon test [-c FILE] [--no-events] [--virtual-device]

Lights up everything on the device and moves the faders: every strip lights its LCD in a color, its LEDs, ring and meter, and moves its fader up and down. Then every strip answers its own controls, until Ctrl+C, so you can check each LED, the ring, the colors, the motor and the touch of every fader:

Input on a strip What the strip shows
Fader moved The meter follows the fader.
Fader touched, let go touch, let go
Rec, Solo, Mute, Select pressed Its LED goes on, flashing, off (mute on, mute fl, mute off).
Encoder turned Changes what the encoder edits, wrapping around, and shows its value.
Encoder pushed The next thing the encoder edits: the position of the ring (ring 7), its mode with and without the two LEDs at the ends of the ring (dot, boost, wrap, spread, dot+c ...), the color of the LCD, the motor fader in steps of 10 % (fad 60%).

The top line of the LCD names the strip, the bottom line shows the last input for 2 seconds, then what the encoder edits. The command prints every input with the answer, and the messages from the device the daemon doesn't use. --no-events ends after the sweep.

While the daemon runs, it has the device: test asks it to run the test instead (the GUI's "Test the device" does the same). The slots go on, but show on the device again only when the test ends; the daemon's log shows the inputs (journalctl --user -u xtouch-daemon -f). --no-events needs the daemon stopped.

Without a daemon it takes the name of the device from [device] of the configuration. --virtual-device (or [device] virtual = true) tests the virtual device, which has to run (in another terminal).

virtual-device¶

xtouch-daemon virtual-device [--broken-touch 1,4] [--log-level debug]

A virtual X-Touch Extender, for trying the daemon without the device: xtouch-daemon run --virtual-device (or [device] virtual = true) drives it instead of the real one, and the GUI shows what it shows. It runs headless until interrupted (Ctrl+C); the GUI can host one itself, with the mouse on its strips. One daemon at a time can use it.

Option Meaning
--broken-touch The faders (from 1) whose touch sensor failed: they never report a touch, see Motor faders.
--log-level debug also logs every message of the daemon.

mode¶

xtouch-daemon mode [NAME | auto | --next | --previous]

Without arguments it prints the modes of the running daemon, marks the one that is on, and says whether it was picked by hand. mode gaming picks the mode gaming, --next and --previous the one after or before it, auto lets the rules decide again. It talks to the daemon over its live view socket, so it needs a running daemon.

why¶

xtouch-daemon why SLOT | CHANNEL

Asks the running daemon why a slot (its number, 1 for the leftmost one) shows what it shows: why not each candidate above, and what it shows. For a channel (its id) it tells on which slots it is and why not on the others that ask for it:

$ xtouch-daemon why 2
Slot 2: voip if call: doesn't hold (call is off); shows auto:app:firefox
$ xtouch-daemon why browser
browser: on slot 4; not slot 8 (on slot 4 (tie, to the left))

The GUI shows the same above the inspector of a slot on the page Slots.

mumble-plugin¶

xtouch-daemon mumble-plugin [--build] [--install]

The Mumble plugin that gives the strips of people the people of your Mumble channel. Without options it tells where the plugin is, whether Mumble is installed, and whether Mumble has the plugin:

Plugin: /usr/share/xtouch-daemon/xtouch-daemon.mumble_plugin
Mumble: installed
In Mumble: /home/me/.local/share/Mumble/Mumble/Plugins/libxtouch-daemon.so
Option Meaning
--install Copies the plugin into Mumble's plugin directory (native, else the Flatpak's), replacing an older one; then Mumble needs "Reload plugins". Without a plugin it builds one first.
--build Builds the plugin from the sources of a checkout (integrations/mumble, needs cmake and a C compiler) into integrations/mumble/build/. With --install: builds it again first.

A release has the plugin in /usr/share/xtouch-daemon/; a checkout builds it.

install-service¶

xtouch-daemon install-service [--now] [--remove-override]

Writes the systemd user unit ~/.config/systemd/user/xtouch-daemon.service for the installed xtouch-daemon and reloads systemd. --now also enables and starts it. The unit is Type=notify, reloads with SIGHUP and restarts on failure.

The Arch Linux package installs its unit as /usr/lib/systemd/user/xtouch-daemon.service. Its xtouch-daemon install-service writes no file then: it reloads systemd, and with --now enables and starts that unit. A unit in ~/.config/systemd/user overrides the one of the package (systemd prefers it), e.g. one written before by a checkout; the command says so.

Option Meaning
--now Also enable and start the service.
--remove-override Only remove ~/.config/systemd/user/xtouch-daemon.service, so the unit of the package is in effect. An enabled service stays enabled, and a running one restarts with the program of the package.

Logs: journalctl --user -u xtouch-daemon -f.

gui¶

xtouch-daemon gui [-c FILE]

Edits the configuration in a window, and applies it. Needs the gui extra, or the package xtouch-daemon-gui-bin (which has the command xtouch-daemon-gui). See GUI.

simulate¶

xtouch-daemon simulate FILE [--mode NAME] [--state NAME]... [--absent CHANNEL]... [--playing APP]... [--person NAME]... [--table | --replay LOG]

What the 8 slots of FILE show in the given states, and why not the candidates above (see Channels, states and slots).

Option Meaning
--mode, --state The mode and the states that are on; the others are off.
--absent A channel that is not present; the others are.
--playing, --person The applications that play (in the order they started) and the people in the voice chat, for the pools auto and people.
--table Every combination of the states and presence the stacks ask about that changes what the slots show.
--replay LOG Instead: replays observations recorded by observe through FILE. Prints when states and slots changed, how often each slot changed, the flaps (a slot back to what it showed within 60 s) and how long each state was on.

observe¶

xtouch-daemon observe LOG [--interval 2.0] [--process NAME]...

Records, every --interval seconds, what plays and records on the sound server, the devices, the running processes (those of the presets, and --process) and the voice chat of the running daemon, and appends a line of JSON to LOG when that changed. absent lists the custom channels whose present says they are not there. Runs until interrupted (Ctrl+C). simulate FILE --replay LOG replays it.

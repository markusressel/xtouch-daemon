Design: layouts¶

Status: implemented as in Phasing; how to use it is in Layouts.

The idea: the configuration holds several layouts, each a set of up to 8 strips. A "default" layout for the desk (outputs, browser, music), a "gaming" layout with the game, the voice chat, the microphone and one strip per participant of the voice channel. Something switches between them: Home Assistant, an application that starts or plays, a button combination on the device, the command line or the GUI.

What others do¶

Product Unit How it switches Notes
Elgato Stream Deck profile, with pages and folders "Smart Profiles": the application in focus picks its profile, matched by executable; leaving it restores the previous profile. A key action switches by hand. (Elgato) Automatic switching is paused while the editor is open. A manual switch by a plugin can disable the automatic one (bug report), a known pain point.
Loupedeck / Logitech profile per application, with workspaces and pages "Dynamic mode" (on by default) follows the active application; off, the chosen profile stays. A button switches workspaces. (Loupedeck CT, user guide) Open-source Linux ports match by process name and window title, falling back to a default profile (loupedeckapp).
GoXLR Utility (Linux) device and microphone profiles UI, and goxlr-client profiles device load <name> for scripts and hotkeys (wiki) The profile is a whole mixer state; a "load colours only" variant exists.
Mackie Control DAWs (Logic, Cubase) banks of 8 channels Bank Left/Right moves by 8 (by the size of the surface group), Channel Left/Right by 1; the last bank is filled up to 8 rather than left half empty (Logic) The model for "more participants than strips".
deej one configuration none; the file is reloaded on change (From the project's README, not re-checked.)
Voicemeeter settings files, macro buttons macro buttons and the Remote API load a settings file (From memory, not re-checked.)
TouchOSC pages (tabs) of one layout a tab bar on the surface, or OSC/MIDI messages (From memory, not re-checked.)

Lessons taken:

  1. One active layout, switched as a whole. Every product swaps the complete set of controls; nobody blends two.
  2. Automatic and manual switching coexist, and the rules for that must be simple. Stream Deck and Loupedeck make the automatic one win whenever the focus changes; a manual choice lasts until the next change. That is the model here too: rules are edge-triggered (see Switching).
  3. Focus is a desktop concept. On Wayland there is no portable way to ask which window has the focus (KWin scripts, GNOME extensions, the Sway/Hyprland IPC all differ). The daemon knows something better for a mixer: which applications play (PipeWire streams), and which processes run (/proc). Focus can come later as a provider of the same rule engine.
  4. A command line to switch (GoXLR) makes every other integration (hotkeys, scripts, desktop launchers) free.
  5. Banks for variable lists (Mackie): a group of strips shows a page of a longer list, and buttons page through it.

VoIP participants¶

The wish: a strip per participant of the voice channel, with the participant's level on the meter and their volume on the fader.

Can a mixer see the participants?¶

Not through PipeWire. Mumble, TeamSpeak and Discord mix every participant into one playback stream, so pw-dump shows one node per client, never one per participant. The participants are only known inside the client.

Client Participants and talking Local volume per participant From outside on Linux
Mumble (1.5) Plugin API: getUsersInChannel, getUserName, mumble_onUserTalkingStateChanged, onUserAdded/Removed Not in the API (requestLocalMute/isUserLocallyMuted mute only). But mumble_onAudioSourceFetched(pcm, …, isSpeech, userID) gets each participant's audio before the mix, may change it (a plugin can apply its own gain) and can measure its peak. The built-in local volume (since 1.3) is not reachable. (MumblePlugin.h) D-Bus net.sourceforge.mumble.mumble: getTalkingUsers, getCurrentUrl, self mute/deaf, transmit mode (DBus.h); mumble rpc the same few commands (RPC docs). No participant list, no per-user volume. Server side (Ice): users and channels, but no talking state and no client-local volume.
TeamSpeak 3 ClientQuery (local TCP 25639, API key): clientlist, notifytalkstatuschange, notifycliententerview (client query library) Plugin SDK only: setClientVolumeModifier(connection, client, dB), and the client stores it (forum). No ClientQuery command for it was found. ClientQuery is reachable from another process. TeamSpeak ⅚ has no stable public API (not re-checked).
Discord Local RPC (Unix socket discord-ipc-N): GET_SELECTED_VOICE_CHANNEL, SPEAKING_START/STOP events SET_USER_VOICE_SETTINGS (volume 0..200, mute) (Userdoccers) The rpc* scopes are for "approved partners" only (Discord OAuth2); projects use Discord's own StreamKit client id and token endpoint instead, without refresh tokens, and Discord restores the volumes when the app disconnects (Noctalia Discord Voice). Fragile and a ToS gray area.

So per-participant levels need code inside the client (a Mumble plugin, a TeamSpeak plugin). Per-participant volume needs the same (Mumble: the plugin applies its own gain in onAudioSourceFetched; TeamSpeak: setClientVolumeModifier), or Discord's restricted RPC. Participant lists and talking states alone are possible from outside for TeamSpeak (ClientQuery) and Discord (RPC), not for Mumble.

Recommendation: a pluggable provider, and a bridge¶

graph LR
    Mumble[Mumble + plugin] -- "JSON lines" --> Bridge
    TS[TeamSpeak + plugin] -- "JSON lines" --> Bridge
    Bridge[BridgeProvider<br/>$XDG_RUNTIME_DIR/xtouch-daemon-voip.sock] --> Strips[voip strips]
    Demo[DemoProvider] --> Strips
    Later[later: TeamSpeak ClientQuery, Discord RPC] -.-> Strips
  • VoipProvider (src/xtouch_daemon/voip/provider.py): a snapshot of Participants (id, name, talking, muted, volume, level), connected, an on_change callback, set_volume(), set_muted(), run(), and what it can do (Capabilities: volume, mute, levels). The strips show only what the provider can do.
  • BridgeProvider (implemented): the daemon serves a Unix socket; a small plugin inside the VoIP client connects and sends the participants as JSON lines, and gets the commands back. The protocol is the same for every client, so a Mumble plugin and a TeamSpeak plugin both work, and the daemon needs no client libraries. A plugin is a few hundred lines of C (Mumble's API is C) and its own build; it is not part of this phase. To try the protocol by hand, socat - UNIX-CONNECT:$XDG_RUNTIME_DIR/xtouch-daemon-voip.sock and a pasted JSON line will do.
  • DemoProvider (implemented): participants from the configuration, with volume and mute kept in memory and a talking pattern, to try layouts and the strips without a VoIP client.
  • Later: TeamSpeakQueryProvider (participants and talking from ClientQuery, no volume), a Mumble plugin speaking the bridge protocol, DiscordRpcProvider only if the scope situation changes.

Bridge protocol (one JSON object per line, UTF-8):

client -> daemon  {"client": "mumble", "participants": [{"id": "12", "name": "Alice", "talking": true,
                   "muted": false, "volume": 100, "level": 0.42}], "capabilities": ["volume", "mute", "levels"]}
daemon -> client  {"set_volume": {"id": "12", "volume": 80}}
daemon -> client  {"set_muted": {"id": "12", "muted": true}}

Every client message is the whole state (like the live view): a client that sends 20 times a second while someone talks needs nothing else. volume is percent (0..200), level the peak since the last message (0..1). One client at a time; a new connection replaces the old one. The socket is mode 0600.

The Mumble plugin: mute and threads¶

Mute on a voip strip is Mumble's own local mute (requestLocalMute, isUserLocallyMuted of plugin API 1.0), so Mumble shows it and a mute set in Mumble lights the button. The first version had its own mute (gain 0 in mumble_onAudioSourceFetched), because the local mute needs API calls the plugin had no safe place for:

  • Mumble calls the event callbacks in its main thread, and runs every API function there: called from another thread, it is queued to the main thread and the caller waits (Mumble's docs/dev/plugins/MumbleAPI.md, "Multithreading"). A callback that waits for a thread that waits for an API call would wait for itself, and the plugin's mumble_shutdown has to wait for its threads before Mumble unloads the library.
  • No callback comes regularly in the main thread. The talking states come only while someone talks, the users' callbacks only when someone comes or goes; a request of the daemon can wait for neither. The only timers that call plugins are those of positional audio (mumble_initPositionalData every second while no positional plugin is linked), which would make the plugin a positional one in Mumble's settings: rejected.
  • Mumble bounds the wait: a call that doesn't get to run within 800 ms is cancelled and fails with MUMBLE_EC_API_REQUEST_TIMEOUT (C_WRAPPER in src/mumble/API_v_1_x_x.cpp, the same in every release with plugin API 1.0: 1.4.230 to 1.6.870).

So the plugin has two threads: the socket thread never calls the API and only queues the mute requests (a counter per participant); the "Mumble thread" makes the requests and reads the local mute of the participants every 500 ms while the daemon is connected (Mumble has no event for it; the callbacks read it too when they refresh the users). No thread holds the plugin's lock during an API call, so a callback never waits for one. Only mumble_shutdown does: it drops the requests that have not started and waits for a call under way, which can't run then and fails after the 800 ms; the thread makes no call after that. Shutting down takes those 800 ms only if a call was under way at that moment.

While a request is under way the plugin reports the requested mute; when Mumble refuses one, it logs why (api.log) and reports Mumble's mute again, so the button goes back. A locally muted participant who talks has the talking state MUMBLE_TS_TALKING_MUTED, which counts as talking: the backlight shows it, as with the first version's mute. Their level is 0: Mumble does not mix them and fetches none of their audio.

Others' self-mute and deafen are not in the API. Plugin API 1.0 has no function for them (isLocalUserMuted and isLocalUserDeafened are the user's own), getUserComment is the free text of the user, and the talking state MUMBLE_TS_TALKING_MUTED of another user means the local mute: AudioOutputSpeech.cpp sets MutedTalking only for bLocalMute (since 1.6 also for a local volume of 0), while ClientUser::setSelfMute/setSelfDeaf emit muteDeafStateChanged, which the plugin manager doesn't forward (it connects talkingStateChanged only). Someone who muted themselves sends no audio, so they are just passive.

Configuration¶

Backward compatible: today's top-level [[strip]] list is the default layout, named default. A file without [[layout]] behaves exactly as before.

[[strip]]                 # the default layout, as before
type = "output"

[[strip]]
type = "apps"
label = "Browser"
match = ["firefox"]

[switching]               # optional, the defaults shown
hold = 10.0               # seconds a rule must stop matching before its layout goes
chord = [1, 8]            # Solo of strips 1 and 8 together: the next layout ([] for none)
banner = 1.5              # seconds the LCDs show the name of a new layout (0 for none)

[[layout]]
name = "gaming"           # for Home Assistant and the command line: a-z, 0-9, _
label = "Gaming"          # on the banner; by default the name
apps = ["steam_app_", ".exe"]   # rule: one of these applications has a stream (plays or paused)
processes = ["mumble"]          # rule: a process with one of these names runs
priority = 0              # of several matching layouts the highest wins, then the first in the file

[[layout.strip]]
type = "inherit"          # the strip of the default layout at this place

[[layout.strip]]
type = "apps"
label = "Game"
match = ["steam_app_", ".exe"]

[[layout.strip]]
type = "apps"
label = "VoIP"
match = ["mumble"]

[[layout.strip]]
type = "input"

[[layout.strip]]
type = "voip"             # always this person
person = ["Alice", "alice-phone"]

[[layout.strip]]
type = "voip"             # the group: the voip strips without person show the others,
[[layout.strip]]          # Select pages through more
type = "voip"

[voip]
provider = "bridge"       # or "demo"
  • Layouts are a list ([[layout]]), their order is the order of next and of the Home Assistant select.
  • Strips per layout like the top-level ones: up to 8 places, missing ones are auto. type = "inherit" takes the strip of the default layout at its place, so a shared output strip is written once. Inheriting from any layout (inherit = "music") is possible later; one level keeps it obvious.
  • Rules are part of the layout (apps, processes) rather than a separate rule list: a layout says when it applies. priority resolves overlaps.
  • Dynamic strips: every voip strip is one strip. With person it always shows that person; the others form the group of the layout, see VoIP strips: the group and fixed people. Fader: the local volume of the participant, Mute: local mute, meter: the level, the backlight turns talking_color while the participant talks.
  • Validation: names unique and not default; homeassistant ids unique per layout (a strip id used in several layouts is the same entities: one desk lamp, two layouts); voip strips need [voip].

VoIP strips: the group and fixed people¶

The first version had count = N on a voip strip, which took N places. That made a strip of the file several strips of the device, which inherit, the placement of collapsing strips and the GUI all had to know about, and it gave no way to keep a person on a fader. Layouts were not released yet, so count went without a compatibility path.

[[layout.strip]]
type = "voip"
person = ["Alice", "alice-phone"]   # a fixed strip
label = "Mum"                        # by default the first name

[[layout.strip]]
type = "voip"                        # the group: all voip strips of the layout without person
  • One strip, one place. A voip strip is one strip of the layout like any other. A file with count gets the error "count is gone: write N voip strips; voip strips without person form a group".
  • Fixed strips. person is a name or a list of names of the same person, matched against the participant's name ignoring case and otherwise exactly. Wildcards were left out: names in a voice chat are chosen by people, and a pattern would sooner or later catch somebody else; aliases cover a second device. Of several participants with one of the names, the first in the provider's order is on the strip; the others go to the group, so nobody is hidden. While the person is away the strip shows its label dark with away and its fader parked, like a device that is not there; Select and Mute do nothing then. Select on a fixed strip does not page.
  • The group is every voip strip of the layout without person, in the order of the file, not necessarily next to each other. It shows the participants without a fixed strip, in the provider's order, a page at a time; Select on any of its strips shows the next page (wrapping), the LCD tells the page for 2 s (pg 2/3), and their Select LED is on while there is more than one page, as the Mackie banks do. Strips left over are dark.
  • Collapse: a strip of the group is absent while it has no participant, a fixed strip while its person is away.
  • Validation: a name on two fixed strips of one layout (after inherit) is an error; label is only for fixed strips, since a strip of the group shows the participant's name.
  • launch starts the command once per layout: the voip strips with the same command share one button (LaunchButton), so its debounce and its flashing LED are shared. launch_when_running stays off for voip strips: while the voice chat is there, Select pages.
  • Volume and mute while away. The Mumble plugin keeps them per session (a user who leaves is forgotten; one who comes back gets a new session at 100 %), and the bridge protocol has no notion of names. So the daemon keeps them: VoipProvider remembers the volume and mute the strips set by the participant's name (ignoring case) and sends them again when a participant of that name appears. A mute that changes in the client (Mumble's local mute, set in its window) replaces the kept one, so coming back does not undo it. This is for every participant, not only those of fixed strips: it costs nothing, and someone of the group who reconnects keeps their volume too. It lasts while the daemon runs; the provider survives layout switches and reloads (not a changed [voip]).
  • The live view tells the names of the participants (VoipState.names) and who each strip of the layout shown shows (VoipState.strips). The GUI suggests the names for person, its strip list says who is on which strip, and the preview prints "VOIP GROUP" or the person's name under a voip strip.

Switching¶

LayoutSwitcher (src/xtouch_daemon/layouts.py) decides; the daemon carries it out.

  • Rules, edge-triggered. Every sound server snapshot and every 2 s (processes) the rules give a wanted layout: the matching layout with the highest priority, else default. When the wanted layout changes, the switcher switches to it. A layout whose rule stops matching stays for hold seconds (a game between two levels, a voice client that restarts). So the automatic switching wins when something happens, and a manual choice stays until then, like Stream Deck and Loupedeck. There is no "lock" mode yet (decided: later, see Phasing).
  • Manual: xtouch-daemon layout gaming (or --next, or without argument: list them), the GUI, the chord on the device, and Home Assistant (select.<ns>_layout). All are the same switch(name, reason).
  • Home Assistant: a select entity with the names of the layouts. The daemon publishes the active layout; a command from Home Assistant switches. Its retained state does not switch (it may be the layout of a rule of the last run): the daemon puts it right once the retained states are in.
  • Remembered across restarts (decided): the daemon keeps the layout it shows in $XDG_STATE_HOME/xtouch-daemon/layout (~/.local/state/xtouch-daemon/layout), unless a rule put it there. A switch by hand and the return of the rules to default write it, a switch by a rule does not. At the start the daemon shows it (if the configuration still has it), and the rules still win: one that matches once the sound server and the processes are known switches to its layout as usual.
  • The device: holding Solo of the chord strips together switches to the next layout. Solo does nothing on audio strips by default; on homeassistant strips the presses are still sent as events.
  • The command channel: the requests of the live view socket (those of the live preview) get one more, {"request": "layout", "layout": "gaming"} (or "+1", "-1"), answered with a reply of kind layout. The snapshot tells layout and layouts, so the GUI and the CLI see the result, and features has layout. Like the preview, the daemon takes it only from its own user (SO_PEERCRED).

On the device¶

A switch is a reload with another set of strips on the same surface: the old mixer closes, a new one takes the same surface, the sound server state and the MQTT bridge. That gives the transitions for free: the faders glide to their new places, dark strips park their faders. For banner seconds the LCDs show the label of the new layout across the top lines of all 8 strips and the reason (manual, Home Assistant, an application) across the bottom lines; the strips draw underneath and appear when the banner ends. The live view shows the banner as well.

Entities in Home Assistant: the entities of the active layout are announced; those of the other layouts are kept (not removed), so automations and the entity registry don't churn on every switch. Only a reload removes entities no layout has anymore.

GUI¶

  • A layout bar above the strips: one tab per layout (default first), + adds one (a copy of the shown one, or empty). The preview and the strip editor show the layout of the selected tab; everything else (paths strip[3], problems, undo) works as before, for that layout. Problems of other layouts lead to them.
  • A Layout tab next to "Global settings" for the selected layout's own options (name, label, rules, priority), from the pydantic model like every other form, with buttons to move it in the order and to remove it. [switching] and [voip] are sections and get forms for free.
  • The preview is live only for the layout the device shows; another layout is shown from the file, and the bar marks the active one. A button "Show on the device" switches the daemon to the shown layout (the command channel).
  • Phase 2 for the GUI: preview of voip strips with demo participants.

Phasing¶

Implemented now:

  1. Config: [[layout]], [switching], [voip], strip types inherit and voip, the default layout from [[strip]], validation; check-config shows every layout.
  2. LayoutSwitcher: rules (apps, processes) with priority and hold, manual switching, next.
  3. The daemon: switching, the banner, the chord, the command channel, xtouch-daemon layout, the select entity.
  4. VoipProvider, DemoProvider, BridgeProvider, the voip strip with paging.
  5. GUI: layout bar, layout page, live preview only for the active layout, "Show on the device".

Decided after phase 1: the Solo chord (strips 1 and 8) stays on by default, the daemon remembers the layout itself (see Switching), and Mumble is the first voice chat client with a plugin.

Later:

  • A lock mode: a manual choice that stops the rules until it is unlocked (xtouch-daemon layout --lock, a second option of the Home Assistant select or a switch next to it, a mark in the GUI's layout tabs). Deferred: the edge-triggered rules already leave a manual choice alone until something happens.
  • TeamSpeak (plugin SDK, or ClientQuery without volume). The Mumble plugin is done: integrations/mumble, see Mumble.
  • Window focus as a rule (focused = [...]) through compositor-specific providers (KWin script, Sway/Hyprland IPC).
  • Rules on time of day or on Home Assistant states (an automation can already set the select).
  • Inheriting from other layouts than the default; per-layout [behavior].
  • A GUI preview of voip strips with participants.
  • Remembering the volumes of the voice chat across restarts of the daemon.

Open questions¶

  • Answered: a lock mode comes later; the chord is on by default; the daemon remembers the layout; Mumble first.
